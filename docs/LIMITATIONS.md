# LIMITATIONS (initial, K0)

This file states what CommitProof does not test or cannot conclude. It is updated in every sprint (K7 produces the final version). IDs are stable; `claims.yaml` references them. Status values: **DESIGN** (true by design at K0), **PENDING** (will be confirmed or resolved by the named sprint).

| ID | Limitation | Status |
|---|---|---|
| LIM-01 | **One pinned commit of an alpha system.** Results apply to Multigres `e3cbdbbb0b94453ca2ec43c9c40c05c98ed7bb73` built from source with upstream Dockerfiles. `main` changes daily; the Supabase-hosted alpha may run different code and configuration. | DESIGN |
| LIM-02 | **Not the production topology.** Components run as Docker containers on one bridge network with flags derived from upstream's Kubernetes demo (`deploy/DERIVATION.md`), not under the Multigres Kubernetes operator, not across real availability zones, and with no real network latency unless F7 injects it. | DESIGN |
| LIM-03 | **Shared kernel: no power-loss or page-cache-loss faults.** Killing a container does not lose data the OS has buffered. Failure modes that need an OS crash (e.g. the `remote_write` hazard in upstream's decision log) are unreachable; their absence in results says nothing about them. | DESIGN |
| LIM-04 | **No clock skew.** Per-node skew is impossible for static Go binaries sharing one host clock (ADR-0005). Multigres computes replication lag by comparing the writing pooler's wall clock with the reader's (`heartbeat/reader.go`); behavior under skew (lag-based replica selection, stall detection) is untested. | DESIGN |
| LIM-05 | **Slow disk is emulated.** F4a uses slowfs, a FUSE pass-through on each node's `/data` (ADR-0006, ADR-0022) that delays file `write` and `fsync` requests by the control file's delay; reads, metadata operations, `pg_sockets` (a bind of the plain volume) and multipooler's own I/O (plain volume, other container) are not delayed. It does not model device queueing, partial writes or I/O errors. Every run, also at 0 ms, pays the FUSE overhead with kernel entry/attribute caching disabled (measured in evidence/K3/NOTES.md). The pre-decided F4b fallback was not needed: the baseline cluster on slowfs at 0 ms reached HEALTHY and completed every K3 run (K3). On a CI runner without `/dev/fuse`, `make ci-nemesis-smoke` skips F4a with a SKIPPED-WITH-REASON line (and `cluster up` refuses to start, §5.6); whether GitHub's runner has it is not known before the owner pushes (LIM-16). | DESIGN (K3) |
| LIM-06 | **Empirical, bounded evidence only.** A clean campaign means no violation was observed in N valid runs of a stated schedule distribution, with the stated statistical bound and exposure (CONTRACT §12.3). It is not a proof of correctness and says nothing about schedules outside the matrix. | DESIGN |
| LIM-07 | **Narrow workloads.** Small tables, short transactions, no DDL during failover, no large objects, no COPY, no two-phase commit, no advisory locks, no temporary tables, no long-running transactions beyond P01. Isolation is checked for list-append transactions only. | DESIGN |
| LIM-08 | **Checker subset.** C3 reimplements a subset of Elle (list-append; G0, G1a, G1b, G1c, G-single, G-nonadjacent, G2-item, duplicates, incompatible order, internal); no rw-register version inference, no predicate anomalies. Porcupine may return UNKNOWN on large partitions (P11); UNKNOWN is never reported as PASS. | DESIGN |
| LIM-09 | **Bullets not covered:** sharded query routing; relational algebra; migrations and materialization pipelines (the migrator is only a proto at the pinned commit); distributed transactions; stream processing beyond one CDC consumer; cross-cluster and cross-cloud interaction; optimization of any kind. See CONTRACT §4. | DESIGN |
| LIM-10 | **Relationship to upstream testing.** Upstream runs deterministic end-to-end scenarios, pg_regress-family suites, TLA+ design models, and an internal chaos test ("Multiquake") whose scope is not public; external manual fault testing found and helped fix data loss in March 2026 (#777, #778). CommitProof does not claim to be the first fault testing of Multigres; it claims public, reproducible, history-checked, mutation-validated testing of one commit. | DESIGN |
| LIM-11 | **Privileges.** The runner mounts the Docker socket (root-equivalent on the host) and joins its group to drive the nemesis; `pg-nX` containers have `CAP_SYS_ADMIN`, `/dev/fuse`, AppArmor unconfined and a root PID 1 (the slowfs launcher; pgctld and PostgreSQL run as uid 999); helpers have `NET_ADMIN` only. All are container-scoped (no privileged containers, no host `sudo`), but the Docker daemon itself runs as root. | DESIGN (K3) |
| LIM-12 | **Single etcd.** The topology store is one etcd member, unlike production; etcd is only faulted by F2e (kill). Topology-store partitions and quorum loss are not modeled. | DESIGN |
| LIM-13 | **CDC is a feature-flagged path.** Logical replication is not supported on the Supabase alpha. CDC tests run with `--enable-slot-based-replication=true` as in upstream's Kubernetes demo; findings there are DESIGN-level at most. LISTEN/NOTIFY loss during reconnect windows is documented upstream behavior and is measured, not judged. | DESIGN |
| LIM-14 | **One durability policy.** Only `AT_LEAST_2` is tested; `MULTI_CELL_AT_LEAST_2` is not. | DESIGN |
| LIM-15 | **Mutant coverage is selective.** Five mutants with directed schedules; candidates rejected as equivalent or not reliably reachable are listed in CONTRACT §9.3 (e.g. position comparison ignoring rule numbers, revocation not persisted). Detecting the five does not imply detecting those. | DESIGN |
| LIM-16 | **Remote CI runs only after the owner pushes.** Until then, CI evidence is local execution of the same `make ci-*` targets. | PENDING (K7) |
| LIM-17 | **Historical control: NOT_DETECTED, on the commit's single-cell demo topology.** H1 (issue #778's commit `4bca1d5`) deployed with its own Dockerfiles (FROM lines only) and its `demo/k8s` flags (one cell, one orchestrator, three gateways instead of five; ADR-0025); in five DH1 runs no new primary appeared while the primary's PostgreSQL was frozen 120 s, and no acknowledged write was lost after the thaw (evidence/K4/NOTES.md §6). S51's data loss was reported on a three-zone local-provisioner setup, which §5.5 does not derive. H1's HEALTHY predicate and leader view read PostgreSQL itself (the commit predates the rule model and `multigres.version()`). | DESIGN (K4) |
| LIM-18 | **Interrupted rule-change propagation is not implemented upstream** (`docs/ha/propagation.md`). Campaigns that interrupt a rule change may leave the shard waiting for operator action; such outcomes are reported as liveness observations, not safety findings. | DESIGN |
| LIM-19 | **Replica-port reads carry no claim.** Anomalies observed through `--pg-replica-port` (C13) are compared with PostgreSQL's known visibility-order behavior on standbys (Jepsen, RDS 17.4) and reported with origin analysis, not as Multigres violations. | DESIGN |
| LIM-20 | **Excluded faults:** clock skew, power loss, disk full, I/O errors, packet corruption/reordering/duplication, DNS failures, etcd partitions, client↔gateway partitions. | DESIGN |
| LIM-21 | **One process user per node.** `multipooler` runs as the pgctld image's postgres user (uid 999) instead of the multigres image's 65532, so that it and pgctld can share `/data`, the pgBackRest key and `/backups` as the containers of one pod do (ADR-0021, `deploy/DERIVATION.md`). Behaviour that depends on the two processes having different users is not exercised. | DESIGN (K1) |
| LIM-22 | **C3 reads transactions, not final reads.** List-append cycles and non-cycle anomalies are inferred from W1 transactions only; final reads feed C1 and C2. An element that no transaction appended (a "garbage" element) is not classified by C3. A history mixing isolation levels is judged by the weakest model present. `-process` and `-realtime` cycle classes are reported as observations, never as violations (G5 claims serializability, not strict or session serializability). | DESIGN (K2) |
| LIM-23 | **Undecided linearizability is expensive.** A register partition that Porcupine cannot decide runs for the full P11 (60 s) and can hold several GiB of memory before returning UNKNOWN (a development measurement, not recorded evidence: about 3.3 GiB peak RSS for 26 concurrent open-ended writes over 60 s). C6 is UNKNOWN for every key C4 could not decide. | DESIGN (K2) |
| LIM-24 | **C7–C9 validated on synthetic forms only.** The history encodings of W5–W8 (session, notify, cdc, overload payloads) were defined in K2 and validated on generated histories; the K5 clients must produce exactly these forms, and nothing about real CDC, LISTEN/NOTIFY, session or overload behaviour is known before K5. | PENDING (K5) |
| LIM-25 | **Literal G8 and G12 rules.** C9 counts any non-40001 failure of an explicit transaction inside an F6 window (including a deadlock, 40P01) as planned-failover-error, and C8 counts every cp_steady failure inside a storm window towards fair-share-starvation even when a nemesis fault overlaps it, as CONTRACT §10.9–§10.10 state. K5 campaigns may show whether these need a refinement (by ADR, never silently). | PENDING (K5) |
| LIM-26 | **Oracle provenance by inputs, not image digest.** The elle-cli oracle image is rebuilt from the pinned clojure base and elle-cli commit; Leiningen fetches its dependencies from Clojars and Maven Central at build time, so the image ID is recorded with every evidence run (with the jar's sha256) rather than locked; reproducibility of the image across clean rebuilds was not tested. elle-cli histories are exported without `index` fields, because with them elle-cli 0.1.11 deadlocks on any history containing a failed operation. | DESIGN (K2) |
| LIM-27 | **Node process tree differs from K1 and from a pod.** In `pg-nX`, PID 1 is the slowfs launcher, which reaps orphans: a killed postmaster disappears from `/proc` at once (F2a's predicate needs that). In K1, and in a pod whose container runs pgctld as PID 1 without an init, the dead postmaster would stay a zombie. Multigres behaviour that depends on a zombie postmaster is not exercised (ADR-0022). | DESIGN (K3) |
| LIM-28 | **What a confirmed fault proves.** Partitions (F1) are confirmed with TCP connects to one listening port per namespace (pgctld 16200, etcd 2379, orch 17000, gw 15432, runner 7999) and drop-rule counters; they exclude the Docker bridge gateway (the host) and Docker's embedded DNS (127.0.0.11), so names still resolve during a partition. F1c leaves the runner connected to the leader; F1a/F1b cut it like any address. Predicates are polled every 0.5 s (P27/P28 deadlines); latencies in NOTES are upper bounds at that resolution. F7 delays the target's egress only, confirmed by connect RTT from one peer. | DESIGN (K3) |
| LIM-29 | **Membership faults reuse n4's volume.** F5a starts n4 from the containers created at run start; F5b stops it gracefully and its data volume stays until teardown. Re-adding a removed n4 within one run, and n4 joining with an empty volume after a previous membership, are not tested in K3. | DESIGN (K3) |
| LIM-30 | **Some K4 runs are summarized, not committed in full.** To stay within P25, minimization candidates and replays of mutant and H1 failures are committed as stubs (manifest, plan, seal; cpgate checks them against the seal and their checks.json); their full archives stay on the machine that ran them. Their verdicts cannot be re-derived from git alone without re-running. Primary runs and every run of a real-build failure are committed in full (CONTRACT §13). | DESIGN (K4) |
| LIM-31 | **elle-cli does not finish on the larger K4 histories.** On ~18 000-operation list-append histories elle-cli 0.1.11 exits with `OutOfMemoryError` in its process-order cycle search (also with a 9 GB heap), and on one history in its validity pass too; such C3 findings are cross-checked with the validity pass where it completes, else labelled `oracle-disagreement` (§10.11). Where elle-cli completes it may report cycles through keys whose reads are incompatible; C3 reports those keys as `incompatible-order` and derives no cycle through them (§10.3). | DESIGN (K4) |
| LIM-32 | **Mutant M2: not detected by D2; detected by D2′ in 4 of 5.** Under the superseded D2 (contract ≤ 1.0.6) multiorch recruited every pooler of the shard and elected the new member, which held the writes, so nothing was lost (0/5). Under D2′ (ADR-0027, approved by the owner; n4 killed together with the leader) M2 lost acknowledged writes in 4 of 5 runs, each REPRODUCED on replay of its minimized plan; in the fifth, competing orchestrators made no failover while n4 was down, so the defect was not reached (evidence/K4/NOTES.md §5, §7). The detection power shown is for D2′'s correlated crash only (LIM-34). | DESIGN (K4) |
| LIM-33 | **Origin of the K4 G2 findings not isolated.** The reads of later-vanished writes (FND-D1-…, FND-C2-…) follow from PostgreSQL completing a commit whose synchronous-replication wait was cancelled (documented, S61) and from the pooler cancelling on context end; no reproduction on plain PostgreSQL streaming replication was run, so the origin is UNDETERMINED. | PENDING (K7) |
| LIM-34 | **D2′ models a correlated crash, not a stale membership view.** D2′ (ADR-0027) detects M2 by killing the leader and the new member n4 together (F2a + F2b on the leader, F2b on n4), so that the failover cannot reach n4. It does not model an orchestrator failing over with a stale membership view, S41's scenario, because multiorch at the pinned commit does not use one: `AppointLeader` (`go/services/multiorch/recovery/actions/appoint_leader.go`) recruits every pooler of the shard. | DESIGN (K4) |
| LIM-35 | **Upstream DNS of the test host reaches the system under test.** Docker's embedded DNS forwards names it cannot answer to the host's upstream resolver — among them the TXT records `_grpc_config.<host>` that grpc-go's dns resolver looks up whenever a Multigres component (`go/tools/grpccommon.NewClient`) opens a new connection, and the names of stopped containers. On the owner's machine (USB-tethered network) that resolver timed out intermittently throughout K4: dockerd logged 305 failed forwards in the boot of the main K4 runs and 1 172 in the boot after the power-off (evidence/K4/NOTES.md §9 item 10, record `dockerd-dns`). A new connection of the SUT (e.g. an orchestrator or a gateway reconnecting to a restarted pooler) may have waited on such a timeout in some runs; this changes timing (failover and recovery latency, availability windows), not what the checkers judge, and K4 did not measure whether it changed any run's course. The runner itself no longer depends on it (fixed in `e0795f1`). | DESIGN (K4) |
